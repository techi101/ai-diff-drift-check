How it was measured

31 small diffs written by hand across 10 security requirements, each labeled honored or violated before the rules were run. 21 are plain (what an agent normally writes) and 10 are tricky (helpers, variables, look alike strings).

Three systems were scored. Regex alone. Regex then judge, where only the cases the rules mark unknown go to the judge. Judge alone, where the judge sees every case with no rules.

Pipeline
  1. Rules. One regex rule per requirement in drift_check/rules.py. It reads only the lines the diff adds and answers honored, violated or unknown.
  2. Judge. drift_check/llm_judge.py sends the prompt from drift_check/judge.py to two Gemini models, gemini-3.5-flash-lite and gemini-3.1-flash-lite (free tier, temperature 0), three times per case each, and takes the majority verdict. Bad JSON or a split vote counts as unknown. Every reply is cached in results/judge_cache/, so the numbers can be audited and rerun for free.
  3. Scoring. drift_check/evaluate.py counts caught, false alarms, silent misses (said honored on a real violation) and unresolved cases, split by plain and tricky. Brackets are Wilson 95% intervals.
What the outcome words mean
  • Caught: labeled violated, rules said violated.
  • Missed: labeled violated, rules said honored (silent miss) or unknown (sent to review).
  • False alarm: labeled honored, rules said violated.
  • Needs review: rules said unknown.
Honest limits
  • The plain numbers are in sample. The rules and plain cases were written together, so 1.00 precision on plain says little. The tricky set is the more honest number and has only 10 cases.
  • One labeler, Python and Flask only, no inter rater check. Real agent diffs are bigger and span files.
  • The rules see one diff with no repo context, so they cannot follow a helper into another file.
  • An earlier run had three comments in the cases that hinted at the answer (# wraps hashlib.md5, fake value, never a real key, # aborts 404 if not the caller's), and the judge scored 31 of 31 there. Those comments were removed (the test file path moved into the diff header, and test_token_not_real_123456 became test_token_123456), labels unchanged, and every number on this page is from the rerun. The old file is kept as data/cases_v1_with_hints.jsonl.
  • Function names such as quick_digest and load_owned were kept because real code has names like that. Without them, two labels would depend only on code outside the diff.
  • Rule errors stay in the regex then judge cascade, because the judge is never asked about cases the rules already decided.
  • Both judges are Flash Lite models from one vendor, two generations apart. That is a weaker comparison than across model tiers. gemini-3.6-flash was tried as the second model, but the free tier allows it 20 requests per day and the run needs 93, so it was stopped and none of its replies are used.
  • One prompt, three runs per case. A different model or prompt could score differently, and the judge saw the requirement text the cases were written against.
  • The highlighted drift line and the CWE tag on each finding were added for this page. They do not change any label or score.
  • All code is synthetic and written for the repo. This is not a claim about how Seezo's validator works.
