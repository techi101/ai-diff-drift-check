How it was measured

31 small diffs written by hand across 10 security requirements, each labeled honored or violated before the rules were run. 21 are plain (what an agent normally writes) and 10 are tricky (helpers, variables, look alike strings).

Pipeline

  1. Rules. One regex rule per requirement in drift_check/rules.py. It reads only the lines the diff adds and answers honored, violated or unknown.
  2. Judge. drift_check/llm_judge.py sends the prompt from drift_check/judge.py to Gemini (free tier, temperature 0) three times per case and takes the majority verdict. Bad JSON or a split vote counts as unknown. Every reply is cached in results/judge_cache/, so the numbers can be audited and rerun for free.
  3. Three systems. Regex alone. Regex then judge, where only the cases the rules mark unknown go to the judge. Judge alone, where the judge sees every case with no rules.
  4. Scoring. drift_check/evaluate.py counts caught, false alarms, silent misses (said honored on a real violation) and unresolved cases, split by plain and tricky. Brackets are Wilson 95% intervals.

Outcome labels on this page

  • Caught: labeled violated, rules said violated.
  • Missed: labeled violated, rules said honored (silent miss) or unknown (sent to review).
  • False alarm: labeled honored, rules said violated.
  • Needs review: rules said unknown.

Honest limits

  • The plain numbers are in sample. The rules and plain cases were written together, so 1.00 precision on plain says little. The tricky set is the more honest number and has only 10 cases.
  • One labeler, Python and Flask only, no inter rater check. Real agent diffs are bigger and span files.
  • The rules see one diff with no repo context, so they cannot follow a helper into another file.
  • Three tricky cases carry a code comment that hints at the answer (# wraps hashlib.md5, fake value, never a real key, # aborts 404 if not the caller's). The judge may have leaned on those; regex ignores them. Real agent diffs will not always be that helpful.
  • The judge got all 31 cases right, but with 31 cases the 95% interval on its recall still runs from 0.82 to 1.00. Rule errors stay in the regex then judge cascade, because the judge is never asked about cases the rules already decided.
  • One model, one prompt, three runs per case. A different model or prompt could score differently, and the judge saw the requirement text the cases were written against.
  • The highlighted drift line and the CWE tag on each finding were added for this page. They do not change any label or score.
  • All code is synthetic and written for the repo. This is not a claim about how Seezo's validator works.
